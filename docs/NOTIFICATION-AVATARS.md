# Notification avatars

A bot's notification shows that bot's picture on the left, with a small Dork Bot badge on it, and the bot's display name as the sender (like Messages and Grok Bot). iOS calls this a Communication Notification. Phone only; the desktop app has no notifications.

## How it works

```
app (any look change / sync / launch)           Hermes plugin dork-bot-push               iPhone
  lib/avatar.ts renders the idle sprite  ──►    push = title: display name,     ──►   Notification Service Extension
  to a 160x160 PNG, writes it to the            data: {bot, name, kind, chat},          (targets/notification-service)
  App Group under  avatar.<profile id>          mutableContent: true                    reads avatar.<bot>, donates an
                                                                                        INSendMessageIntent (INPerson + INImage),
                                                                                        iOS draws avatar + badge
```

- **No network in the extension.** The picture was rendered earlier by the app (`lib/avatar.ts`, `components/avatars.ts`): the bot's current idle frame, its character, look and color, on the app's dark card color. It is stored base64 in the App Group's shared UserDefaults (`group.com.brenw2.dorkbot`) under `avatar.<profile id>`, because that is the one thing Expo can write to the group without our own native code (`@bacons/apple-targets` ExtensionStorage). The extension finds the bot with the `bot` field the push already carries.
- **Refresh.** `AvatarExport` (root layout) runs on launch and on every change to the bot list: a look picked on this phone, or a look synced from another device (`lib/sync.ts` → `updateBot`). Only bots whose character, look or color changed are re-rendered (`avatar-sig.<bot>`); bots that are gone lose their picture. A look changed on another device shows up in notifications after the next time the app opens and syncs.
- **Display name.** The plugin reads `dork_bot.name` (Rename…) and uses it as the notification title and in `data.name`. The profile id stays in `data.bot` (taps, avatar lookup). A routine's title is `<name> · <routine>`; the extension moves the routine name into the message text because the sender line only has the name.
- **Never dropped.** No avatar file for the bot, an extension error, or the extension running out of time all show the push as the plugin sent it (title = display name, Dork Bot icon).
- **The extension target** is generated by `@bacons/apple-targets` from `targets/notification-service/` (`expo-target.config.js`, `NotificationService.swift`, `Info.plist`). It adds `extra.eas.build.experimental.ios.appExtensions`, which is how `eas build` knows there is a second target to sign.

## Ids

| | |
| --- | --- |
| App | `com.brenw2.dorkbot` |
| Extension | `com.brenw2.dorkbot.notification-service` (target `NotificationService`) |
| App Group | `group.com.brenw2.dorkbot` (on both) |
| Capabilities | App Groups + Communication Notifications on both; Push Notifications on the app |

Check the config any time: `npx expo config --type introspect` (needs `npm ci`; no `ios/` folder).

## One-time credentials step (Brennan, normal terminal)

The extension is a second App ID with its own provisioning profile, and Apple wants App Groups and Communication Notifications turned on for it and for the app. `eas build` in the CI workflow can't do that part: creating the App Group needs a real Apple ID login (eas-cli skips it with an App Store Connect API key). Do it once, from a clean checkout of `main` after this is merged (no `ios/` folder; the project must be the managed one):

```bash
cd ~/Work/dork-bot && git pull && npm ci
EXPO_APPLE_TEAM_ID=C7Z2H37BVG npx eas-cli@27.2.0 credentials:configure-build -p ios -e production
```

(`eas credentials -p ios` → profile `production` → **Build Credentials: Manage everything needed to build your project** → **All: Set up all the required credentials to build your project** does the same thing.)

What it asks, in order:

1. `Do you want to log in to your Apple account?` → **Yes**. Apple ID, password, 2FA code. Team: `C7Z2H37BVG` (the personal team; never Sallie Mae `96L2D73W86`). If it lists teams, pick that one.
2. It says the scheme has many targets (the app and `NotificationService`) and sets up each: registers `com.brenw2.dorkbot.notification-service`, enables the capabilities, creates the App Group `group.com.brenw2.dorkbot` and links it to both App IDs.
3. For the app, the old provisioning profile no longer has the new capabilities, so it may ask `Would you like to reuse the original profile?` → **No** (or **Yes**, it then fixes it itself; both end with a good profile). It reuses the existing Distribution Certificate.
4. For the extension it creates a new App Store provisioning profile.
5. Ends with `All credentials are ready to build @brenw2/dork-bot (com.brenw2.dorkbot, com.brenw2.dorkbot.notification-service)`.

Nothing here costs money or builds anything. After that, the existing manual workflow (`.github/workflows/ios-testflight.yml`, `eas build --local --non-interactive`) signs both targets from EAS with `EXPO_TOKEN`; it needs no change. If step 5 hasn't been done, the build stops early with a credentials error instead of producing an unsigned extension.

## What is checked where

- Node: PNG output and the per-bot file/refresh logic (`test/avatar.test.ts`), the plugin payload (`hermes-plugin/dork-bot-push/tests`).
- Not checkable without a Mac and a phone: the Swift extension itself (it has never been compiled or run), that iOS draws the avatar and badge, and the routine title handling. Those are the "build 10 on the phone" checks.
